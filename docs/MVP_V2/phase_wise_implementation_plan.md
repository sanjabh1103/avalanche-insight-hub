# Phase-Wise Gap Resolution & Next-Steps Implementation Plan

This document outlines the detailed, phase-wise implementation strategy to plug the remaining gaps between customer expectations and the current Avalanche Insight Hub implementation, incorporating the resolved parameters for the pilot.

---

## Phase 1: Security & Access Governance (Pilot Hardening)
**Objective:** Resolve gateway-level JWT verification bypasses and insecure defaults to secure the pilot sandbox before any staging or public release.

### 1.1 Gateway JWT Route Separation
- **Target File:** [supabase/config.toml](file:///Users/sanjayb/avalanche-insight-hub/supabase/config.toml)
- **Implementation:**
  - Split Edge Functions into two distinct authorization categories:
    1. **Public/User Endpoints:** Set `verify_jwt = true` for endpoints that serve data to the user-facing web client (e.g. `run-forecast`, `recent-activity-refresh`). This enforces Kong-level native JWT verification.
    2. **System Webhooks / Background Jobs:** Keep `verify_jwt = false` only for functions triggered by `pg_cron` or remote orchestrators (e.g. `trigger-job`, `ingest-event`, `label-forecast-outcomes`). 
  - **Deno Handler Hardening:** Ensure that all functions with `verify_jwt = false` explicitly call [auth.ts:authorizeJobRequest](file:///Users/sanjayb/avalanche-insight-hub/supabase/functions/_shared/auth.ts#L44) and match against the vault-stored `JOB_DISPATCH_TOKEN` in the `Authorization` header.

### 1.2 Admin Credential Cleanup & Rotation Policy
- **Target Files:** `.env`, `.env.example`, [AdminAccessGate.tsx](file:///Users/sanjayb/avalanche-insight-hub/src/components/AdminAccessGate.tsx)
- **Implementation:**
  - Remove the pre-populated default login email (`admin@insight-hub.local`) and password (`test123`) from the client UI.
  - Implement a standard initial onboarding command script `/scripts/create-operator-account.sh` to provision new operator accounts with randomly generated high-entropy passwords in the Supabase Auth system.
  - Configure platform secrets for production deployments to strictly block default/test credential logins when the application runs in production mode.

## Phase 2: Scientific Consistency & Machine Learning Calibration
**Objective:** Repair KMeansSMOTE physical inconsistency in the Random Forest surrogate model to ensure physically consistent decision boundaries.

### 2.1 Physical Boundary Constrained SMOTE
- **Target File:** [surrogate_rf.py](file:///Users/sanjayb/avalanche-insight-hub/backend/models/surrogate_rf.py)
- **Implementation:**
  - Implement validation functions in `surrogate_rf.py` that check synthetic data points generated by KMeansSMOTE against physical atmospheric and geographic rules:
    - **Lapse Rate Boundary:** Temperature must decrease with elevation. Reject synthetic samples where high temperatures are placed at high elevation grid points during mid-winter.
    - **Precipitation-Temperature Co-occurrence:** Reject synthetic samples generating snow settlement index changes when temperatures are high and precipitation is zero.
  - Automatically filter or adjust unphysical synthetic weather-terrain states before passing them to Random Forest training.

### 2.2 Calibration & Peirce Skill Score (PSS) Ratchet
- **Target File:** [surrogate_rf.py](file:///Users/sanjayb/avalanche-insight-hub/backend/models/surrogate_rf.py)
- **Implementation:**
  - Incorporate strict checks on the Brier Score Calibration curve on out-of-bag validation sets.
  - Block weekly GHA retraining if the new model's Peirce Skill Score falls below the baseline gate of `0.45` or if calibration curves show severe probability distortion (Brier score > `0.15`).

## Phase 3: Transition to Thermodynamic Physical Snowpack Modeling
**Objective:** Transition the "Weather-Driven Heuristic Proxy" to a true 1D thermodynamic stratigraphic snowpack simulation (WSL/SLF SNOWPACK or Crocus-class).

### 3.1 Define Data Adapter Contract
- **Target File:** [SNOWPACK_HIMSTRAT_Partner_Data_Adapter.md](file:///Users/sanjayb/avalanche-insight-hub/docs/MVP_V2/02_letters_outreach_templates/SNOWPACK_HIMSTRAT_Partner_Data_Adapter.md)
- **Implementation:**
  - Establish the partner data adapter to ingest observed station profiles (layer depths, grain types, hand hardness, density, liquid water content).
  - Write translation functions in `backend/common/snowpack_adapter.py` that read this physical schema and format it as ML features.

### 3.2 thermodynamic Simulator Integration
- **Target File:** `backend/common/snowpack_proxy.py` (to be replaced by `backend/common/snowpack_physical.py`)
- **Implementation:**
  - Connect the ingestion pipeline to a thermodynamic model instance (running on a containerized service or partner API) that executes CROCUS or SNOWPACK using downscaled meteorological forcing data.
  - Extract physical multi-layer variables (e.g. persistent weak layers, slab thickness, and load) to replace the cumulative empirical heuristic proxy in the production ML pipeline.

## Phase 4: Remote Sensing & Sequence Model Graduation
**Objective:** Solve Sentinel-1 dry-snow limitations and graduate the MTS-LSTM sequence model from shadow mode.

### 4.1 Multi-Orbital and Multi-Modal SAR Fusion
- **Target File:** [sar_acceptance_policy.py](file:///Users/sanjayb/avalanche-insight-hub/backend/common/sar_acceptance_policy.py)
- **Implementation:**
  - Implement a multi-orbital fusion workflow that combines ascending and descending Sentinel-1 radar passes to mathematically resolve geometric terrain distortions (layover, shadows, and foreshortening) on steep Himalayan slopes.
  - Maintain the strict precision floor gate (`blocked_shadow_only`) to prioritize safety. Do not lower precision thresholds for dry-snow limitations.
  - Frame Sentinel-1 SAR as a retrospective calibration tool rather than a real-time warning system in all customer-facing materials.

### 4.2 MTS-LSTM Model Promotion
- **Target File:** [lstm_model.py](file:///Users/sanjayb/avalanche-insight-hub/backend/lstm_model.py)
- **Implementation:**
  - Run weekly evaluation benchmarks comparing the shadow `BranchedMTSLSTM` model against the surrogate Random Forest baseline on held-out test splits.
  - If the MTS-LSTM beats the Random Forest baseline on both Peirce Skill Score (PSS > 0.45) and Brier calibration score (Brier < 0.15) for three consecutive runs, trigger the automated GitHub Action release gate to promote it to the production scoring path.
